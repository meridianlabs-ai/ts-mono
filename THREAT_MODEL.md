# Threat Model: ts-mono (Inspect AI log viewer & Inspect Scout UI)

## 1. System context

ts-mono is the TypeScript monorepo (pnpm + Turbo, React 19, Vite, roughly 1,870 source files) behind the Inspect AI eval-log viewer (`apps/inspect`) and the Inspect Scout transcript-scanning UI (`apps/scout`), plus shared `@tsmono/*` packages: `inspect-common` (generated OpenAPI types and the `normalize` parse boundary), `inspect-components` (chat, transcript and tool-output renderers), `react` (markdown, ANSI and asciinema rendering and the DOMPurify-based `sanitizeRenderedHtml` chokepoint), `util`, `theme`. The built `dist` is committed into the Python packages `inspect_ai` and `inspect_scout` through a git submodule and ships inside their wheels; `apps/inspect` is also published to npm as `@meridianlabs/log-viewer` for embedders.

The viewer runs in four contexts. (1) Served by the local `inspect view` FastAPI server (default `127.0.0.1:7575`, optionally `0.0.0.0` with a bearer-style `--authorization` header), whose API reads any log path or URI the server process can reach on local disk or S3/GCS/Azure and exposes write endpoints (`log-edit`, `log-message`, `log-delete`; Scout adds `startscan`, `project/config`, and code generation). (2) As a static bundle written next to logs on S3 or static hosting, or pushed to Hugging Face Spaces. (3) Inside the Inspect VS Code extension webview, where all HTTP goes through a generic JSON-RPC `http_request` proxy in the extension host. (4) Embedded in third-party web apps via npm, with the embedder supplying `apiBaseUrl`, `headerProvider`, and `customFetch`.

The data the viewer renders (eval logs and Scout transcripts) is produced by the LLMs, tools and sandboxes under evaluation. The owner's trust decision is: the log *structure* (Inspect-generated ids, span trees, score names, attachment ids, file layout) is trusted, because Inspect AI writes it and logs are only shared between trusted organizations; the transcript *content* (model output, tool arguments and results, markdown, HTML, URLs, embedded JSON) is not, because it may be the output of a malicious model. The primary actor throughout is therefore "a model whose output ends up in a log someone opens". The same split applies to Scout: a well-formed scan file's structure is trusted (if it is not, a trust boundary upstream has already failed), but scanner verdicts, explanations and extracted snippets are model output and are not, and the agent under test can emit tokens intended to manipulate the scanner model. Two past fixes (cd1d0c12, 528cebd4) entered through that path.

Because the producer is trusted, per-item content sizes in a well-formed log are bounded by Inspect itself: tool output is truncated at 16KB by default (`max_tool_output`), sandbox stdout/stderr are capped, and model output is bounded by provider token limits. What a valid log does not bound is the number of events, attachment sizes, or the *shape* of small content, so availability threats here are about rendering complexity and uncaught exceptions rather than gigabyte blobs.

Deployment is local and trusted: people run `inspect view` on their own machine, occasionally sharing the port with a trusted coworker; static bundles are shared between trusted people, not hosted on a multi-tenant origin. The VS Code extension (`inspect_vscode` @ d17d9f5) applies a nonce-based CSP to the webview (`default-src 'none'`, `connect-src` limited to the webview origin, but `script-src` carries `'unsafe-eval'` for the viewer's `new Function` workers) and confines the `http_request` proxy to the panel's log scope with an exact-case method allowlist. The extension's own threat model (`inspect_vscode` SECURITY.md, PR #188, merged 2026-09-11) places the log and scan webviews on the *untrusted* side of its boundary: it assumes a log may achieve script execution in the viewer, keeps the view-server token in the extension host, and treats every message the webview sends as hostile. That is consistent with T1 here and means the two models compose: this repo's job is to make that assumption rarely true; the extension's job is to contain it when it is. CI agent gating was tightened in `meridianlabs-ai/agents` (@ 5d16259, 2026-09-10/11): the actor must hold write access, fork-head PRs are refused, `MARVIN_TOKEN` was removed from the reviewer and loop agent jobs, and git credentials are no longer persisted. The owner considers `MARVIN_TOKEN` still over-privileged.

The repo has a dense recent security history: six XSS or sanitizer fixes, two prototype-pollution fixes (one of which escalated to a host-side `scout.yaml` write), one CI fork-PR exposure, and eight dependency advisories, all between May and September 2026. There is no `SECURITY.md`, no Content-Security-Policy in either `index.html`, and no prior threat model. CI runs several autonomous Claude agent workflows holding repository write permissions and an organization machine PAT.

## 2. Assets

| asset | description | sensitivity |
|---|---|---|
| eval log & transcript contents | Prompts, completions, tool calls, sandbox commands and outputs, scores, metadata. May contain API keys, PII, proprietary eval material, or unreleased model behaviour. | critical |
| host log-store read reach | Through the view server the browser can read any log path or URI the server process can (local filesystem as the user; S3/GCS/Azure). Confinement is entirely server-side (`OnlyDirAccessPolicy`, disabled when `--authorization` is set). | critical |
| host-side mutation endpoints | `log-edit` (scores, tags, metadata), `log-message`, `log-delete`; Scout `startscan`, `PUT project/config` (rewrites `scout.yaml` including model `base_url`), code generation. Browser-reachable control over host state and what scans run. | critical |

| VS Code extension host bridge | `displayLogFile` command and the generic `http_request` JSON-RPC proxy. A compromised webview has view-server access from the extension host process. | high |
| rendered result integrity | Researchers decide whether an eval passed from client-side derived and normalized headline metrics, scores and transcripts. | high |
| client-side log cache & persisted state | IndexedDB `InspectAI` (one per origin, holding every log dir ever opened there), zustand `app-storage`, `inspect-scout-storage`, settings including 25 recent model names; VS Code webview state. | high |
| shipped viewer bundle | Vite `dist` vendored into the `inspect_ai` / `inspect_scout` wheels and `@meridianlabs/log-viewer` on npm. Executes in every user's browser or webview. | critical |
| CI identities & secrets | `MARVIN_TOKEN` organization machine PAT, `GITHUB_TOKEN` with contents/pull-requests/issues write, OIDC `id-token` for npm trusted publishing and Anthropic workload federation. | critical |
| repository & gate integrity | `main`, `pnpm-lock.yaml`, `suppressions.json` ratchet, workflow files. Growing the ledger silently disables type-safety rules on boundary code. | medium |
| viewer availability | Tab responsiveness during live eval monitoring (pending samples, polling, SSE). | medium |
| operator identity | `GET /user-info` returns `{name, email}` shown in the UI. | low |

## 5. Deprioritized

| threat | reason |
|---|---|
| Repudiation of log edits, deletes, or scan launches made through the viewer | Attribution and audit belong to the Python view server and the deployment (it exposes `/user-info` and logs client messages); the client cannot enforce it. Raised as an open question instead. |
| Spoofing of the operator identity or bypassing authentication in the client | The client has no authentication of its own; `--authorization` and any hosted-deployment auth are server and deployment controls outside this repo. |
| Elevation of privilege within the single-page app | No internal privilege levels; any script in the viewer origin already has full client authority, so elevation is subsumed by T1. |
| Dev-only surfaces: `rewriteLoopbackOrigin` Vite proxy, Storybook, `packages/util/bench` | Not shipped in `dist`; the origin rewrite is restricted to loopback and only affects local development. |
| `new Function(atob())` worker bootstrap as an injection vector | The payload is a build-time constant compiled into the bundle, not runtime input. Retained in section 8 as a CSP obstacle, not as a threat. |
| `window.open` without `noopener` in Scout route links | Targets are same-document hash routes on the same origin; the opener relationship adds nothing an attacker does not already have. Cheap to fix but not a distinct threat. |
| Fork-PR code execution in `ci.yaml` | Fork runs receive a read-only token and no secrets; residual impact is runner compute and turbo cache entries, ordinary OSS CI exposure. Folded into T3 for the `pull_request_target` and agent paths that do hold write tokens. |
| Cross-tenant leakage via the per-origin IndexedDB cache on a shared host | Owner states (2026-09-12) that static bundles are shared between trusted people and no host serves untrusted users. Re-open if a multi-tenant deployment appears. |
| Attacks on a centrally hosted multi-user `inspect view` server | Owner states this is not the deployment model: `inspect view` runs on personal machines, occasionally shared with a trusted coworker. |
| Prototype pollution via Inspect-generated log structure (span ids, score names, attachment ids, skeleton.json) | Owner decision: log structure is trusted because Inspect AI writes it and logs come from trusted organizations. Both past instances (ddd4db7e, cd1d0c12) entered here; T2 keeps only the model-controlled-content variant. |

## 6. Open questions

Answered by the owner on 2026-09-12 (claims that moved a score are listed as follow-ups to verify):

- [Owner-states] Log structure is trusted; only transcript content is attacker-influenced. Affects: T2 impact/likelihood, section 5. Verify by: confirming no Inspect code path lets a model choose a span id, score name, attachment id, or store key (e.g. `store_as` keys set from tool arguments).
- [Owner-states] `inspect view` runs on personal machines, rarely shared off-loopback, and only with trusted coworkers. Affects: T7 likelihood, T12 likelihood/actor. Verify by: grepping internal docs and runbooks for `--host 0.0.0.0` / `--authorization` usage.
- [Owner-states] No static bundle is hosted on an origin shared with untrusted users. Affects: T12, T13 (cross-tenant variant moved to section 5). Verify by: listing where bundles are actually deployed (S3 buckets, HF Spaces) and who can read or write those origins.
- [Code-verified] The VS Code extension applies a nonce CSP and scope-confines the `http_request` proxy (`inspect_vscode` `src/core/webview.ts`, `src/core/package/proxy-scope.ts` @ d17d9f5). The CSP still needs `'unsafe-eval'` because of this repo's `new Function` workers. Affects: T6 controls, mitigation 1.
- [Code-verified] `meridianlabs-ai/agents` @ 5d16259 gates on actor write access, refuses fork-head PRs, and removed `MARVIN_TOKEN` from reviewer and loop agent jobs. [Owner-states] `MARVIN_TOKEN` is still over-privileged. Affects: T3 likelihood/actor. Verify by: reading the PAT's repository and permission scopes in the machine account's settings.
- [Code-verified] `@meridianlabs/log-viewer` publishes from `UKGovernmentBEIS/inspect_ai` on every release tag (OIDC, SLSA provenance); this repo's `npm-publish.yml` is dead. The `npm` environments on both repos have no protection rules and no tag ruleset exists. Affects: T9 threat text and controls. Follow-up: decide whether release tagging on `inspect_ai` needs a second approver, and delete the dead workflow here.
- [Owner-states] Scout scan files are trusted in structure, untrusted in scanner output; the agent under test may try to manipulate the scanner. Affects: section 1 actor framing, T1 and T8 surfaces (scan results already listed). Verify by: confirming Scout's viewer paths (`scout-components`, `apps/scout`) route scanner explanations through the same sanitizer as eval-log markdown.
- [Code-verified] METR's Hawk relies on `credentials: "include"`: `www/src/utils/headerProvider.ts:3-12` returns no bearer token ("Auth now rides the HttpOnly cookie"), `www/src/hooks/useInspectApi.ts:107-111` passes only `apiBaseUrl` + `headerProvider` (no `customFetch`), the API is on a sibling subdomain so `isApiCrossOrigin()` is always true, and `hawk/api/auth/access_token.py:62-81` reads the `inspect_ai_access_token` cookie for the viewer. Hawk also pins a repack, `npm:@metrevals/inspect-log-viewer@0.3.264-beta...`, citing unresolved `workspace:*` deps. [Code-verified 2026-09-13] That leak was real only for 0.3.240 and 0.3.241 (fixed by ts-mono 03fc7ae2, #351); 0.3.242 onward has no `workspace:` specs in `dependencies` or `peerDependencies`, and the repack's dependency block is identical to upstream's. `check:publishable` runs via `prepublishOnly` on the release path but not on the prerelease path (`--ignore-scripts`), and `check-all` does not include it. Affects: T7 controls, T9 controls, mitigations 9 and 10. Follow-up: `credentials: "include"` cannot be dropped; make it a transport option defaulting to current behaviour, and coordinate any default flip with METR.
- [Owner-states] Losing the whole viewer to one bad transcript item would be bad. [Code-verified] It can happen today: one router-level `AppErrorBoundary`, no per-event boundary. Affects: T10 threat text and likelihood (giant-blob cases downgraded because the producer caps item sizes; exception path kept). Follow-up: mitigation 7 now leads with per-event error boundaries.

- [Code-verified] `inspect_vscode` SECURITY.md (PR #188) documents that the token-authorized view server "reads and writes any path or URL it is asked to, by design", and that the extension makes this acceptable by binding `127.0.0.1` explicitly, keeping the token out of the webview, and confining the proxy to a fixed route set scoped to the panel. So the `--authorization` behaviour is intended for the extension. Affects: the former open question below; T7 controls unchanged.
